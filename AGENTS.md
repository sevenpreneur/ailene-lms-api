# AGENTS.md

Instructions for coding agents (Claude Code, Codex, or others) working in this repo. Read this before making changes.

## What this is

Ailene LMS API: a Spring Boot REST API for the LMS module of a larger Neon Postgres database (the same project also hosts a separate CRM/B2B module and an account/identity service — see Database below). Deployed on Railway.

## Stack

Java 21, Spring Boot 4.1.0 (`spring-boot-starter-web`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-starter-actuator`), PostgreSQL (Neon), Flyway (`spring-boot-flyway`/`flyway-core`/`flyway-database-postgresql`, wired up but not yet used — see Database), `jjwt` (`jjwt-api`/`jjwt-impl`/`jjwt-jackson`) for the session JWT, Lombok. Maven (`./mvnw`). Module/artifact name: `lms`.

## Running locally

1. Copy `.env.example` to `.env` and fill in `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` (Neon Postgres), `GOOGLE_OAUTH_ID`, and `SECRET_KEY` (any random string — it's the static token `POST /api/v1/auth/login/google` checks, see `docs/api/auth.md`). `PORT` is optional, defaults to `8080`. `QSTASH_URL`/`QSTASH_TOKEN`/`APP_BASE_URL` are optional too — without them, `QStashClient` just logs a warning and skips scheduling (see `common.qstash`). `OPENAI_API_KEY` is likewise optional at startup, but required for `POST /api/v1/pre-assessment/report-callback` to actually do anything — without it, that endpoint fails immediately and the report row is marked `status: "failed"`.
2. `./mvnw spring-boot:run` — serves on `:$PORT`. `.env` is loaded automatically (see `LmsApplication.loadDotenv()`); no manual export needed, and it never overrides a var that's already set in the real environment.
3. `LmsApplicationTests` is just the default `contextLoads()` placeholder, and it boots the full Spring context (needs a live DB connection since `ddl-auto: validate`) — but real unit tests do exist per-feature now (Mockito, no Spring context; see `material.MaterialServiceTest` for the pattern). `./mvnw test` picks up `.env` automatically for the `@SpringBootTest` ones — see the note in Conventions about why that needed its own static block instead of just relying on `LmsApplication`'s. There is no linter configured in `pom.xml`.

## Project structure

Package-by-feature under `com.ailene.lms.<feature>`: each feature owns its own `Entity`, `EntityController`, `EntityDto`, `EntityRepository`, etc. directly in one package (no separate controller/service/repository/dto layer packages — was tried, reverted). Cross-feature code (response envelope, exception handling) lives in `com.ailene.lms.common`.

## Conventions — follow these exactly, they're load-bearing

- **Every endpoint is `POST`, and every controller's `@RequestMapping` is versioned under `/api/v1`** (e.g. `/api/v1/categories`, `/api/v1/quizzes`). No `GET`/`PUT`/`DELETE`/`PATCH` anywhere, even for reads or ones with no request body (`CategoryController`, `check-session`, `logout`) — use `@PostMapping` regardless. This isn't a security boundary, it's just the house style; don't reintroduce other verbs, and don't add a new controller without the `/v1` segment. A wrong-method request is handled by `GlobalExceptionHandler.handleMethodNotSupported` (405 `METHOD_NOT_ALLOWED`), and a genuinely nonexistent route by `handleRouteNotFound` (404, for Spring's `NoResourceFoundException`) — neither falls through to the generic 500 handler, keep both mappings in sync if you add new routes.
- **Reuse `common.security.SecretKeyGuard`** for any endpoint gated by the static `SECRET_KEY` bearer token (`requireValidSecretKey`) or that just needs the raw token out of the `Authorization` header (`extractBearerToken`, used by `check-session`/`logout` to get the JWT) — don't re-implement header parsing per controller.
- **Response envelope:** always return `ApiResponse.success(HttpStatus, message, data)` or `ApiResponse.error(HttpStatus, message)` from `common.response`, wrapped in `ResponseEntity` — never build a `ResponseEntity` or return a raw body directly. `StatusName.fromCode()` must stay in sync with every `HttpStatus` actually used.
- **JSON is snake_case** (`spring.jackson.property-naming-strategy: SNAKE_CASE` in `application.yaml`), matching the DB's column naming — Java fields stay camelCase (`fullName`), Jackson converts both ways at the boundary, so DTOs never need `@JsonProperty`. That global config only applies to Spring MVC's own request/response bodies, though — a manually-built `RestClient` (see the note below) does not inherit it, so `auth.GoogleUserInfo` uses an explicit `@JsonProperty("email_verified")` instead of relying on the strategy. One quirk: `@Valid` field-validation error messages (`GlobalExceptionHandler.handleValidation`) report the Java property name, not the JSON one — e.g. sending a blank `access_token` comes back as `"accessToken: must not be blank"`, not `"access_token: ..."`. Don't try to "fix" that by renaming the Java field; it's a Bean Validation limitation, not a bug.
- **Errors:** declare exception types under `common.exception` and register a handler in `GlobalExceptionHandler` (`@RestControllerAdvice`) that maps it to `ApiResponse.error(...)`. The catch-all `Exception` handler must never leak raw exception text to the client — keep the response message generic — but it must log the exception (`log.error(...)`) first: once an `@ExceptionHandler` catches something, Spring never logs it on its own, so skipping this makes a real bug on the deployed app invisible in Railway's logs, not just hidden from the client.
- **DTOs are records with a `public static from(Entity)` factory** — see `CategoryDto`/`UserDto`. Controllers return DTOs, never JPA entities directly. Keep the factory `public` even though the DTO usually shares a package with its entity: some DTOs are consumed from another feature package too (`auth.AuthLoginResponse` wraps `user.UserDto`), and package-private would break that.
- **Entities:** Lombok `@Getter`/`@Setter`, explicit `@Column(name = "snake_case")`, `OffsetDateTime` for `TIMESTAMPTZ` columns. Match the live column type exactly (e.g. `CHAR(21)` nanoid-style ids are `String`, not a numeric type) — and for `CHAR(n)` specifically, a plain `String` field isn't enough: Hibernate defaults a `String` to `VARCHAR`, which fails `ddl-auto: validate` against a real `CHAR(n)` column even with `columnDefinition` set. Add `@JdbcTypeCode(SqlTypes.CHAR)` plus `@Column(length = n)` (see `access.Access.id`/`projectId`). A Postgres native enum column needs `@Enumerated(EnumType.STRING)` + `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`, with Java enum constants spelled exactly like the Postgres labels (lowercase) since Hibernate matches by `name()` — see `access.AccessRole`.
- **Any column with a DB-level `DEFAULT` (e.g. `created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP`) needs `insertable = false` on its `@Column`.** Without it, Hibernate's generated INSERT explicitly writes `NULL` for that column whenever the Java field is unset, which bypasses the Postgres default entirely (a default only fires when the column is omitted from the INSERT, not when it's set to `NULL`) — that surfaces as a `NOT NULL constraint` violation at insert time, not at compile or schema-validate time. This bit `Token.createdAt`/`User.createdAt`/`Role.createdAt` in production (500 on `login/google` from a null `lms_tokens.created_at`) before all three got `insertable = false`.
- **Entity class names don't always match the table**, on purpose: `user.User`→`lms_users`, `auth.Token`→`lms_tokens`, `category.Category`→`lms_categories`. Every entity in this app maps an LMS-owned `lms_*` table — nothing maps a table owned by the account/identity service or the CRM module, and it should stay that way (see Database).
- **Comments:** one line, no multi-line comment blocks. If it needs more than one line, it needs a shorter explanation instead.
- **API docs live in `docs/<area>.md`** (e.g. `docs/auth.md`), one file per feature area, not per controller class. Format: one intro paragraph, then per endpoint a one-sentence description, `**Authorization:**` line, request as a JSON block + Field/Type/Required table, response as a JSON block (no field table) with any non-obvious fields explained in a paragraph after it, and an `**Errors**` table (`Code | Status | Message | When`) plus one example error response. Update the relevant doc whenever a controller's request/response shape or error cases change.
- **`.env` loading is intentionally not SPI-based.** `me.paulschwarz:spring-dotenv` and a hand-rolled `EnvironmentPostProcessor` (both registered via `META-INF`) were tried first and silently never got invoked on this Spring Boot version — instead `LmsApplication` loads `.env` in a `static {}` block before `main()` calls `SpringApplication.run()`. That block does **not** fire for `@SpringBootTest`, because Spring only reads `LmsApplication`'s bytecode metadata there and never actually loads the class — so `LmsApplicationTests` has its own `static {}` block calling the same package-private `LmsApplication.loadDotenv()`. Any other test class that needs `.env` (e.g. a future `@SpringBootTest`) needs that same static block copied in, since it isn't inherited automatically.
- **This Spring Boot version doesn't auto-configure a `RestClient.Builder` bean** either (`spring-boot-starter-web` alone isn't enough — injecting `RestClient.Builder` fails app startup with "no qualifying bean"). `auth.GoogleTokenVerifier` builds its `RestClient` with the static `RestClient.create()` instead. If you add another outbound HTTP call, do the same rather than assuming DI will provide a pre-configured builder.
- **This Spring Boot version is on Jackson 3, whose `ObjectMapper`/`JsonNode`/etc. moved to the `tools.jackson.*` package** (groupId `tools.jackson.core`, pulled in transitively via `spring-boot-starter-jackson`) — `import com.fasterxml.jackson.databind.ObjectMapper` (Jackson 2) fails to compile, because the only Jackson-2 `jackson-databind` on the classpath is a `runtime`-scope transitive of `jjwt-jackson`, invisible at compile time. `com.fasterxml.jackson.core:jackson-annotations` (`@JsonProperty` etc.) is the one exception that keeps its old Jackson-2 coordinates — that one's still `import com.fasterxml.jackson.annotation....`, unchanged. If you need `ObjectMapper` (e.g. to parse a raw JSON string, see `preassessment.PreAssessmentRecommendationGenerator`), `import tools.jackson.databind.ObjectMapper` and let Spring inject the autoconfigured bean — don't add a `com.fasterxml.jackson.core:jackson-databind` compile dependency to "fix" the import, that's the wrong Jackson major version for this app.
- **`lms_accesses.group_id` and `current_level_id` are `NOT NULL`** (`current_level_id` defaults to `1`, the lowest level), so every access belongs to exactly one group and sits on exactly one level. The `Access` entity maps neither column -- both are only ever read through native projections -- so `ddl-auto: validate` will not catch a mistake here. Note this makes `sponsor` awkward: a sponsor is org-wide but still has to name a group. The many `getGroupId() == null` branches in `champion`, `prompt`, `usecase`, `student` and `sponsor` are now unreachable for data that came through the DB; they are kept as cheap guards, not because the case can occur.

- **`lms_levels` is a global lookup, not per-project data.** It holds Ailene's own ladder (Foundation / Operator / Capstone) and has no `project_id`; `level_number` is globally `UNIQUE` because it is the key the application reads by — `PromptService` and `ChampionAssignmentService` hardcode level 2 and 3, which only means anything if a level means the same thing for every client. So never scope a query by `lv.project_id` and never derive a project from a level. The project comes from `lms_chapters.project_id` for curriculum, from `lms_prompts`/`lms_use_cases`.`only_project_id` for the practice libraries, and from `access.getProjectId()` in a service that has already resolved an access. `only_project_id` follows the same convention as `only_group_id`: `NULL` means the row is shared by every project, a value means it belongs to that one. It exists because `level_id` used to be the only thing tying the libraries to a tenant — dropping `lms_levels.project_id` without it would have merged every client's prompt library, self-created practice prompts included.

- **A chapter is curriculum; its schedule lives in `lms_chapter_sessions`, one row per sitting.** `only_group_id IS NULL` on a session means every group in the project attends it, a non-null `only_group_id` means only that group — so the same chapter can be scheduled once for everyone, or several times with different dates and trainers per group, without ever duplicating the chapter or the `lms_materials`/`lms_videos`/`lms_quizzes` hanging off it. That matters because every completion row keys off a content id: duplicate the content per group and the two copies become different ids that no report can compare. Two query shapes follow from this, and both are already repeated across `chapter`/`material`/`video`/`quiz`/`access`/`champion` — copy them rather than inventing a third. **To display** a chapter, `JOIN LATERAL (SELECT ... FROM lms_chapter_sessions s WHERE s.chapter_id = c.id AND s.status = 'active' AND (s.only_group_id IS NULL OR s.only_group_id = <the caller's group>) ORDER BY (s.only_group_id IS NULL) LIMIT 1) s ON true` — the `ORDER BY` puts `false` first so a group-specific session beats the all-groups one, the `LIMIT 1` stops a chapter that has both from returning two rows, and the inner join drops chapters with no applicable session, which is exactly the targeting rule. **To count** tasks, an `EXISTS (SELECT 1 FROM lms_chapter_sessions s WHERE s.chapter_id = c.id AND s.status = 'active' AND (s.only_group_id IS NULL OR s.only_group_id = a.group_id))` predicate is enough and cannot double-count. Leaving either out is not a compile error and not a validation error — it silently shows one group another group's sessions, or inflates their `tasks_required`.

- **A native `@Query` that projects a single interface and has no real `FROM`/main row source (e.g. `SELECT (SELECT x FROM t WHERE ...) AS x`, used for a nullable "completion" lookup) returns Java `null` for the whole method call when every selected column comes back `NULL` — not a projection object whose getter returns `null`.** The raw SQL itself returns one row with a null column (confirmed directly against Neon), but Spring Data JPA collapses that all-null row to no result. Calling `.getXxx()` on the result without a null check throws an NPE that `GlobalExceptionHandler`'s catch-all turns into an opaque 500. This bit `material.MaterialService.getMaterialDetails`/`video.VideoService.getVideoDetails` (`MaterialRepository.findCompletion`/`VideoRepository.findCompletion`) — any student who hadn't completed the item 500'd, which is the common case. Always null-check the result of this kind of query before calling a getter on it; see the fix and `material.MaterialServiceTest`/`video.VideoServiceTest` for the pattern.

## Database

`docs/db/ailene-lms.sql` documents the **LMS module only** (`lms_*` tables) of the Neon project **Ailene** (`orange-union-08059820`) — it intentionally leaves out the CRM module (`companies`, `pipelines`, `contacts`, etc.) and `users`/`teams`/`phone_country_codes`, which are owned by a separate account/identity service and referenced only as external tables (see the notes inside that file). Those external tables change without warning and without touching this repo: `roles` was dropped outright when the identity service moved to a `users.role` enum, and the CRM's `b2b_company`/`b2b_pipeline` were renamed to `companies`/`pipelines` — both only surfaced as runtime breakage here. Don't map an external table with an entity, and prefer copying the few fields the LMS needs onto an `lms_*` table over joining across the boundary. `docs/db/nanoid.sql` is the Postgres `nanoid()`/`nanoid_optimized()` function pair (Viascom, Apache-2.0) already deployed on that Neon project; `CHAR(21)` id columns (e.g. `trainers.id`) are nanoid-shaped but have no DB-level `DEFAULT` — the application sets them explicitly.

**There is no real migration history yet.** `spring.jpa.hibernate.ddl-auto` is `validate` (Hibernate never auto-migrates), Flyway is configured but `src/main/resources/db/migration` is empty, and the live schema was hand-authored directly against Neon (via the Neon MCP tools) and documented after the fact in `docs/db/ailene-lms.sql`. Until real Flyway migrations exist, any schema change must be made in **both** places by hand — the DDL doc and the live Neon project — and they must never drift. Since `ddl-auto` is `validate`, `./mvnw test -Dtest=LmsApplicationTests` (with a real `.env` in place) is a fast way to catch an entity/schema mismatch without writing any data.

The Indexes section at the bottom of `ailene-lms.sql` is the one deliberate exception to that no-drift rule: its 32 foreign-key indexes are **not applied to Neon yet**. Postgres does not index FK columns on its own, and every other index on a `lms_*` table is a primary key or a `UNIQUE` constraint — so any child-side lookup (`lms_coaching_notes.student_access_id`, `lms_chapters.level_id`, `lms_tokens.user_id`, …) is a seq scan today. Run that section, then delete this paragraph.

## Known gaps

- `prompt`/`usecase` `details`, `self-assign` and `submit` read the project straight off `only_project_id`, so a genuinely shared library row (`only_project_id IS NULL`) cannot be opened through them — they would look up an access for a `null` project and 404. Nothing creates such a row today (every existing row was backfilled to its project, and both create paths set it explicitly), so the shared case is schema capability the API does not expose yet; exposing it means taking `project_id` in those requests.
- `sponsor.SponsorRepository.countLearningTasks` is still project-wide, unlike `champion.ChampionRepository`'s, which takes a `groupId`. Once groups have chapters of their own, the sponsor org dashboard's denominator counts every group's tasks, so a per-student completion ratio built on it reads low. Left as-is because "how many learning tasks does this program contain" is a genuinely different question from "how many does this group have" — but the org dashboard needs to pick one before groups diverge.
- Test coverage is thin and grows opportunistically (e.g. alongside bug fixes) rather than systematically — most services/controllers have no test yet. No CI config in this repo.
- Auth covers login/session-check/logout (`AuthController`/`AuthService`/`JwtService`) but nothing else: `check-session` and `logout` validate the `Bearer` JWT against `lms_tokens`, but no other controller (e.g. `CategoryController`) requires auth at all yet — there's no shared filter/interceptor enforcing it app-wide. `login/google` itself is gated by a shared `SECRET_KEY` as a static bearer token (same value for every client, not per-client auth) — `SECRET_KEY` is deliberately dual-purpose (that gate + the JWT signing key), not two separate secrets.
- `preassessment.PreAssessmentService.create` schedules a QStash job to `/api/v1/pre-assessment/report-callback` for AI recommendation generation, but that route doesn't exist — no controller consumes it yet, so every submitted pre-assessment's report stays `status: "pending"` forever until that worker (and the actual LLM call it would make) is built. `POST /api/v1/pre-assessment/score` still works fine in the meantime since it's a local computation, not dependent on that job.
- Flyway is a dependency but unused in practice (see Database) — this is a real gap, not a deliberate choice.
- `ailene-lms.sql`'s Indexes section is written but not applied to Neon — see Database. Until it runs, assume every FK lookup is a seq scan.
- **`lms_tokens` is the one table in the schema that grows without bound.** `AuthService.loginWithGoogle` inserts a row per login and nothing ever deletes it except an explicit `logout`; there's no TTL and no cleanup job. `JwtService.issue` sets a 365-day expiry, so a stale row stays a valid session for a full year. The `token TEXT UNIQUE` column also means the btree holds the whole JWT (~300-400 bytes per entry), so the index is roughly the size of the table. Deliberately left alone for now — the table is near-empty pre-launch — but it needs a prune-on-login (or storing the `jti` instead of the whole JWT) before real traffic.
- **Neon's compute only scales to zero if nothing holds a connection.** `spring.datasource.hikari.minimum-idle` is `0` with a 30s `idle-timeout` specifically so the pool drains and Neon's 5-minute suspend timer can actually fire — a `minimum-idle` of 1 pinned one connection open 24/7 and burned a whole month's compute quota. Don't raise `minimum-idle` above 0, and don't add a `@Scheduled` job that touches the DB on a sub-5-minute interval without weighing that cost. Same applies to `/actuator/health`: Railway only hits it at deploy time, but its DataSource indicator runs a real query, so pointing an external uptime monitor at it would keep the compute awake permanently.
